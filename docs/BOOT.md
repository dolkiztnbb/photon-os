# Загрузка PhotonOS: HDD/SATA, IDE, CD-ROM, USB

## Коротко

| Носитель                         | Как BIOS грузит нас             | Откуда ядро читает ФС        | Запись |
|----------------------------------|---------------------------------|------------------------------|--------|
| SATA-диск (AHCI)                 | HDD, LBA (int 13h AH=42h)       | `sd0` — drivers/ahci.c       | да     |
| IDE/PATA-диск, SATA в режиме IDE | HDD, LBA                        | `hd0..hd3` — drivers/ata.c   | да     |
| CD-ROM на IDE (ATAPI)            | El Torito, сектор 2048          | `rd0` (копия в ОЗУ)¹         | в ОЗУ² |
| CD-ROM на SATA                   | El Torito                       | `rd0`                        | в ОЗУ  |
| USB-флешка (сырой образ или ISO) | USB-HDD, LBA                    | `usb0` (EHCI)³, иначе `rd0`  | да³    |
| Дискета / USB-FDD                | CHS (int 13h AH=02h)            | `rd0`                        | в ОЗУ  |

¹ если памяти мало и stage2 не смог сделать копию, ядро читает прямо с `cd0`
(только чтение).
² содержимое ramdisk теряется при перезагрузке; ядро пишет предупреждение.
³ если флешка USB 2.0 воткнута прямо в порт EHCI-контроллера (см.
`drivers/usb.c` и «Ограничения»); иначе — `rd0`, изменения в ОЗУ.

Сборка и запуск:

```sh
make os-image.bin   # output/build/image/os-image.bin — сырой образ диска/флешки
make iso            # output/build/image/photon.iso  — загрузочный CD (и гибридный для dd)
make run            # QEMU, SATA/AHCI (как раньше)
make run_ide        # QEMU, IDE-диск
make run_cdrom      # QEMU, CD-ROM
make run_usb        # QEMU, USB-флешка с сырым образом
make run_usb_iso    # QEMU, USB-флешка с гибридным ISO
make test           # проверки без QEMU (Unicorn + хост-тест драйверов), см. ниже
```

Запись на реальный носитель:

```sh
sudo dd if=output/build/image/os-image.bin of=/dev/sdX bs=1M conv=fsync   # флешка/диск
sudo dd if=output/build/image/photon.iso  of=/dev/sdX bs=1M conv=fsync   # флешка (ISO)
# Windows: Rufus в режиме «DD-образ» (не ISO-режим!), или прожечь photon.iso на CD.
```

Образ занимает 2 МБ — всё остальное место носителя не используется.

## Раскладка образа диска

Все числа — в 512-байтных секторах, задаются в `Makefile` (`IMG_*`):

```
LBA 0          MBR: stage1 (boot/bootsect.asm), заголовок образа, таблица разделов
LBA 1..31      stage2 (boot/stage2.asm), до 15.5 КБ (поддержка загрузки ядра из ФС)
LBA 60..383    init.bin — ядро, до 162 КБ (324 сектора) — fallback, основное ядро теперь в /sys/kernel/
LBA 384..      fs.vd — файловая система DATSLAF (содержит /sys/kernel/kernel.bin и версии)
всего 4096     (2 МБ)
```

Новая схема (v2): ядро хранится в ФС `/sys/kernel/`:

- `kernel.bin` — текущее ядро (копия `init.bin` при сборке)
- `kernel-1.0.0.bin`, `kernel-<date>.bin` — версионированные ядра
- `boot.cfg` / `default` / `active` — текстовый файл с именем ядра для загрузки по умолчанию
- `versions.txt`, `README.txt` — документация

Stage2 теперь умеет:

1. Читать DATSLAF напрямую (суперблок → таблица узлов → поиск `/sys/kernel`)
2. Читать `boot.cfg` для выбора версии
3. Показывать меню выбора, если несколько ядер
4. Fallback на старый LBA-метод, если ФС не найдена

См. `docs/KERNEL_VERSIONS.md`.

Числа попадают:

* в stage1 — через `-D` при ассемблировании (`boot/bootsect.bin` в Makefile);
  stage1 записывает их в заголовок `pht_imghdr_t` по смещению 0x40 MBR;
* в stage2 и ядро — из этого заголовка в рантайме (`boot/bootinfo.h`),
  поэтому их не нужно дублировать руками. `FS_START_SECTOR` в ядре задаётся
  тем же `IMG_FS_LBA` через `CFLAGS`, а `fs_load_from_disk()` сверяет его с
  заголовком.

`tools/mkimage.py` собирает образ и падает, если какая-то часть не
помещается в отведённое ей место (раньше `dd` молча накладывал файлы).

## Как идёт загрузка

### Stage 1 (`boot/bootsect.asm`, 512 байт)

1. Ставит `DS=ES=SS=0`, `SP=0x7C00`, обнуляет структуру `pht_bootinfo_t`
   по адресу `0x600`, запоминает `DL` (номер диска BIOS).
2. Смотрит на El Torito boot-info-table (байты 8..63 сектора). Её заполняет
   `tools/mkiso.py`; в сыром образе там нули.
   * `bi_file != 0` — мы загружены из ISO. Размер сектора носителя узнаём
     через `int 13h AH=48h`: 2048 → настоящий CD, `image_lba = bi_file`;
     512 → гибридный ISO записан на флешку/диск, `image_lba = bi_file * 4`.
   * иначе образ лежит с нулевого сектора (`image_lba = 0`).
3. Проверяет расширения `int 13h` (`AH=41h`). Если есть — читает первые 8 КБ
   образа (MBR + stage2) по адресу `0x8000` одним вызовом `AH=42h`
   (на CD это 4 сектора по 2048, на диске — 16 по 512). Если нет — это
   дискета/USB-FDD или древний BIOS: читает 15 секторов CHS (`AH=02h`,
   цилиндр 0, головка 0, сектор 2) с повтором после сброса контроллера.
4. Проверяет сигнатуру `"S2"` в stage2 и прыгает на `0:0x8200`.

Ошибки печатаются как `ED` (диск) или `ES` (нет stage2) с остановкой.

### Stage 2 (`boot/stage2.asm`, ≤ 7.5 КБ)

1. Печатает тип носителя и LBA образа, для CHS-носителей запрашивает
   геометрию (`AH=08h`).
2. Определяет объём ОЗУ (`int 15h AX=E801h`), включает A20 (BIOS →
   порт 0x92 → контроллер клавиатуры, с проверкой после каждого шага).
3. Грузит `init.bin` по `KERNEL_ADDR = 0x100000`. BIOS умеет писать только в
   первый мегабайт, поэтому данные читаются кусками по 32 КБ в буфер
   `0x10000` и копируются выше через **unreal mode** (DS/ES с лимитом 4 ГБ,
   `a32 rep movsd`). Лимиты сегментов восстанавливаются перед каждым
   копированием — некоторые BIOS их сбрасывают.
4. Копирует **весь образ** в память по `RAMDISK_ADDR = 0x1000000` (16 МБ).
   Это и есть ответ на вопрос «как грузиться с USB, не имея USB-стека»: пока
   мы в реальном режиме, BIOS читает с флешки/CD сам, а ядру остаётся копия в
   ОЗУ. Ошибки чтения здесь не фатальны (ядро получит усечённый ramdisk и
   предупредит), нехватка памяти — пропуск шага.
5. Заполняет `pht_bootinfo_t` (тип носителя, размер сектора, `image_lba`,
   адреса и размеры ядра и ramdisk, объём памяти, копию первого сектора
   образа), ставит плоскую GDT, переходит в защищённый режим и прыгает на
   ядро: `CS=0x08`, остальные сегменты `0x10`, `ESP=0x7FFF0`,
   `EAX="PHOT"`, `EBX=0x600`.

### Ядро

`main()` в `kernel/kernel.c` вызывает `blockdev_init_boot()`
(`drivers/blockdev.c`), который:

1. Копирует bootinfo (если ядро запущено старым способом — работает как
   раньше: первый найденный диск, образ с нулевого сектора).
2. Опрашивает бэкенды: AHCI (`sd0`), IDE/ATAPI (`hd*`, `cd*`), ramdisk (`rd0`).
3. Выбирает корневое устройство:
   * загрузка с CD → `rd0`, иначе ATAPI-привод, на котором лежит образ;
   * загрузка с HDD/USB → устройство, у которого сектор `image_lba`
     совпадает с MBR из bootinfo (так отличаем «наш» диск от чужих и
     находим образ внутри гибридного ISO);
   * если такого диска нет — нас загрузили с флешки: только теперь
     вызывается `usb_init()` (EHCI + USB-хабы + USB Mass Storage). Он
     забирает контроллер у BIOS, обходит корневые порты и хабы, ищет флешку
     с тем же MBR и регистрирует её как `usb0`; чужие флешки пропускаются,
     контроллеры без нашей флешки останавливаются (BIOS их обратно не
     получает — см. «Ограничения»);
   * не нашли — `rd0`.
4. `blk_read_sector()` / `blk_write_sector()` принимают LBA **от начала
   образа** и сами добавляют смещение образа на носителе. Через них работают
   `kernel/datslaf/fs.c` и системные вызовы `SYS_AHCI_READ/WRITE`.

Команда `lsblk` в оболочке ядра показывает найденные устройства и выбранное
загрузочное.

## Что изменилось по сравнению со старой схемой

* Старый `bootsect.asm` читал 63 сектора только через CHS и прыгал в
  «мост» `kernel.bin`, который умел читать **только AHCI** (`kernel/loader.c`,
  `drivers/dumb-pci.c`): на IDE, USB и CD ядро не находило контроллер и
  разыменовывало нулевой указатель. Мост и его файлы удалены.
* `drivers/ahci.c`: `initialize_ahci_and_read()` больше не падает при
  `abar == 0` и возвращает осмысленный код (0 — диск читается).
* `cpu/mmio.c`: identity-mapping расширен с 16 до 32 МБ (ramdisk лежит на
  16..18 МБ); `setup.h`: регион `__PHT_MEM_BOOTDISK`.
* `init()` обнуляет `.bss` (`init.ld` экспортирует `__bss_start/__bss_end`):
  раньше статические переменные ядра стартовали с мусором на реальном железе.
* Стек ядра на входе — `0x7FFF0` вместо `0x6FFFFF` (тот адрес лежал внутри
  пула kmalloc `0x600000..0xE00000`).

## Ограничения

* **USB:** ядро само работает с флешками через EHCI-контроллеры (USB 2.0,
  `drivers/usb.c`): в корневом порту или за USB-хабами, включая встроенный
  «rate matching hub» чипсетов Intel 5-9 серий (там все разъёмы платы
  подключены через него) и цепочки до 5 хабов. Full-Speed (USB 1.1) флешки
  работают, если они за High-Speed хабом (через его transaction translator).
  Не поддерживаются: xHCI (USB 3.x — на платах Intel 100-й серии и новее,
  AMD Ryzen и Intel 7-9 серий в режиме xHCI EHCI нет или порты отданы xHCI),
  а также USB 1.1 устройства прямо в корневом порту (их обслуживают UHCI/OHCI).
  Тогда ФС работает в ОЗУ (`rd0`), изменения не сохраняются. Загрузка при
  этом не зависает: все ожидания в драйвере ограничены по времени; пустые
  порты каждого хаба ждут подключения устройства не дольше 1 с.
* Драйвера USB-клавиатуры нет: она работает через BIOS-эмуляцию PS/2. Ища
  флешку, ядро забирает у BIOS EHCI-контроллеры по очереди, пока её не
  найдёт, и USB-клавиатура на таком контроллере (в т.ч. за хабом, например
  за RMH на платах Intel 5-9 серий) перестаёт отвечать — используйте PS/2
  или встроенную клавиатуру ноутбука. Low/Full-Speed устройства в корневых
  портах драйвер отдаёт companion-контроллеру (UHCI/OHCI), как это делает
  BIOS, а остановленный контроллер отдаёт ему все порты; Low-Speed
  устройства за хабами (клавиатуры, мыши) он не трогает. Обратно BIOS
  контроллер не возвращается: так не делают ни Linux, ни Windows, BIOS после
  этого обычно устройства заново не опрашивает, а SMM-обработчик BIOS на
  таком возврате может повесить машину.
* **CD-ROM на SATA-контроллере** (AHCI, сигнатура `0xEB140101`) ядро само не
  читает — только ramdisk. IDE-ATAPI (`cd*`) читается напрямую.
* IDE-драйвер — PIO без прерываний; LBA48 поддерживается только командами
  чтения/записи, LBA > 2³² не адресуется.
* Образ должен быть кратен 2048 байтам (требование `mkiso.py` для чтения
  секторами CD) и ≤ 4 МБ (`__PHT_MEM_BOOTDISK_END`).
* Загрузка через UEFI не поддерживается — нужен Legacy/CSM режим.

## Тесты без QEMU

* `make test_boot` — `tools/boottest.py` прогоняет stage1+stage2 в эмуляторе
  [Unicorn](https://www.unicorn-engine.org/) с фальшивым BIOS в режимах HDD,
  CHS, CD (El Torito), гибридный ISO на флешке, диск с ошибками чтения.
  Проверяется: ядро по `0x100000` байт в байт, ramdisk, все поля bootinfo,
  GDT, регистры на входе в ядро, отсутствие записи в IVT/BDA.
* `make test_blkdev` — `tools/blkdev_test/` собирает `ata.c`, `blockdev.c`,
  `ramdisk.c` как хост-программу поверх модели IDE-контроллера
  (ATA-диск + ATAPI-привод с UNIT ATTENTION и порционной выдачей данных) и
  проверяет выбор загрузочного устройства во всех сценариях.
* `make check_bootinfo` — согласованность `boot/bootinfo.h` и
  `boot/bootinfo.inc` (выполняется при каждой сборке образа).

Это не заменяет запуск на QEMU/железе: эмуляторы не проверяют лимиты
сегментов в unreal mode и реальное поведение BIOS.
